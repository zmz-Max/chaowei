# 固件工程与调试环境

> 本文记录机器人固件工程的搭建过程、引脚与参数配置，以及调试中踩过的坑，供后续复现与答辩使用。

## 工程结构与工具链

| 环节 | 选择 | 说明 |
| --- | --- | --- |
| 引脚与时钟配置 | STM32CubeMX 6.18.1 | 图形化配置，生成初始化代码 |
| 工程组织 | CMake + STM32CubeCLT 1.22.0 | CubeMX 的 Toolchain/IDE 选 CMake，便于 CLion 直接打开 |
| 编译器 | arm-none-eabi-gcc 14.3.1 | 随 STM32CubeCLT 安装 |

工程目录为仓库根目录下的 `AIcar/`，其中 `Core/Src/ps2.c`、`Core/Inc/ps2.h` 为自行编写的手柄驱动，其余为 CubeMX 生成的标准结构。

## 手柄驱动设计

- 通信协议与 SPI Mode 3 等效，但**不能用 HAL 的单字节收发**：STM32F1 的 `HAL_SPI_TransmitReceive(…, 1)` 在单字节场景下存在"读 RXNE 前数据未就绪"的已知问题，因此驱动改为直接读写 `SPI_SR` / `SPI_DR` 寄存器，最稳。
- 每次通信时序：片选拉低 → 延时几微秒 → 连续收发 9 字节 → 片选拉高 → 间隔 ≥1ms。间隔太短接收板不会响应。
- 初始化时依次发送"进入配置模式 → 打开模拟模式 → 设置双摇杆模式 → 退出配置"四条命令，使接收板能输出摇杆数据；随后读一次，用第 3 个字节是否为 `0x5A` 判断通信是否正常。

## 调试记录与踩坑

### CLion 中两个 CMake 配置互相污染（10-14）

- **现象**：点击构建后报错 `ninja: error: build.ninja:35: loading 'CMakeFiles/rules.ninja': The system cannot find the file specified.`
- **原因**：CLion 里有两条构建配置——一条是不带后缀的 `Debug`（默认使用系统里的 MinGW 编译器 `D:\Code\ucrt64\bin\cc.exe`），另一条是 `Debug-STM32`（使用 STM32CubeCLT 的 ARM 编译器）。先用前者配置工程时，会在构建目录里写入"使用 MinGW 编译器"的 CMake 缓存；之后换用正确的配置，CMake 检测到编译器变量与缓存不一致，要求清空缓存后重配，配置中断导致 ninja 的规则文件没有生成。
- **解决**：删除被污染的两份构建目录（`cmake-build-debug`、`cmake-build-debug-stm32`），用 ARM 工具链重新配置生成；并**始终只使用 `Debug-STM32` 配置**，避免再次污染。
- **经验**：当同一工程里有多个 CMake 配置、且编译器不同时，每个配置必须使用各自独立的构建目录；一旦缓存被"错误编译器"写过，最省事的做法是直接删掉构建目录重配。

### SPI 未使能导致程序卡死在 RXNE 等待（10-14）

- **现象**：固件烧录成功、确认已在运行，但板上 PC13 灯既不亮也不闪（只有 PWR 电源灯亮）。
- **定位方法**：在 CLion 里点 **Debug** 启动，程序跑起来后点暂停，CLion 直接停在 `ps2.c` 的
  `while ((s_hspi->Instance->SR & SPI_SR_RXNE) == 0) { }` 这一行，左侧调用栈显示
  `ps2_xfer ← ps2_transact ← PS2_Init ← main`，几分钟内就定位到具体死等位置。
- **根因**：STM32F1 的 `HAL_SPI_Init()` **只配置寄存器，不使能 SPI 外设**
  （源码里 `__HAL_SPI_ENABLE` 只出现在 HAL 自己的收发函数中）。本驱动为绕开 F1 HAL
  单字节收发的已知问题，改为直接读写 `SPI_SR` / `SPI_DR`，因此没有人打开 SPE：
  写进 `DR` 也不会产生时钟，`RXNE` 永远为 0 → 死等。
- **修复**：`PS2_Init()` 中显式调用 `__HAL_SPI_ENABLE(hspi)`；同时给两处等待加计数超时
  （约 10 万次空转），保证外设异常时只返回失败、不卡死，上层可用 LED 提示故障。
- **经验**：遇到“程序在跑但没反应”，最快的办法是**用调试器暂停看调用栈**，比反复改代码试快得多。

### ST-LINK error (DEV_CONNECT_ERR) 的另一个常见原因（10-14）

除接线问题外，**ST-Link 被其它程序占用**同样会报 `DEV_CONNECT_ERR`：例如 CLion 的调试会话
尚未结束（CLion 会持续占用 ST-Link）。此时先在 CLion 里点停止按钮结束会话，再连接即可。
本次排查过程中多次出现该报错，均属此因。

## 固件烧录方式

### 不要在 CLion 里点“运行 / Run”

- **现象**：点运行后报 `Cannot run program "...AIcar.elf": CreateProcess error=193, %1 不是有效的 Win32 应用程序`。
- **原因**：`.elf` 是给单片机（ARM 内核）用的固件，不是 Windows 可执行文件。CLion 的“运行”是在**本机**执行可执行文件，所以必然失败；这不是代码或配置出错。
- **正确做法**：CLion 只用来写代码和**构建**（构建配置选 `Debug-STM32`），烧录交给下面的方式。

### CLion 也可以烧录（需要正确的运行配置，已跑通）

在 `Run → Edit Configurations → +` 里新建一个 **Embedded GDB Server** 类型的配置（Target 选工程目标，GDB server 选 `ST-LINK`），之后点运行就是“下载并运行”。成功时的输出形如：

```
0x08002724 in ?? ()
Loaded 10288 bytes
monitor reset
STM32 Successfully completed reset operation (System reset)
continue &
Continuing.
进程已结束，退出代码为 0
```

判读要点：

- `Loaded xxxx bytes` 的字节数应与编译输出的 FLASH 占用一致（本次 10288 B），可用来确认下载的确实是新固件；
- `进程已结束，退出代码为 0` 属于正常现象——下载、复位、运行之后 GDB 会话退出，不是报错；
- 若建的是普通 `Application` 类型配置，运行时报 `CreateProcess error=193`，说明配置类型选错了。

### 推荐：双击 `AIcar/flash.cmd`

脚本会自动找到最新的 `AIcar.elf`，调用 STM32CubeProgrammer 的命令行工具烧录。看到 `Download verified successfully` 即成功。

### 等价的手工命令

```bat
"D:\STM32CubeCLT\STM32CubeCLT_1.22.0\STM32CubeProgrammer\bin\STM32_Programmer_CLI.exe" ^
  -c port=SWD freq=1000 -w "AIcar.elf" -v -rst
```

### 用 CubeProgrammer 图形界面时

- **Mode** 选 `Normal` 或 `Under reset` 都可以
- 提示 `Warning: UR connection mode is defined with the HWrst reset mode` 只是说明“复位下连接”用的是硬件复位，**不影响正常使用**
- 连接成功后先看两行信息：`Voltage`（应约 3.30V）与 `Device ID`（STM32F103C8T6 为 `0x410`）

### 连接失败的排查顺序（10-14 实际踩过）

1. `ST-LINK error (DEV_CONNECT_ERR)` 表示 ST-Link 被电脑识别、但与芯片通信失败，属于**物理连接**问题，先查线；
2. 逐根用万用表通断档确认杜邦线两端导通（杜邦线内部断丝很常见）；
3. 核对丝印：`SWCLK` ↔ 核心板 `CLK`、`SWDIO` ↔ `DIO`、`GND` ↔ `GND`；注意 **ST-Link 上的 `SWIM` 是 STM8 专用**，插到它上面永远连不上；
4. 确认 ST-Link 的 `GND` 与核心板 `GND` 导通（0Ω）；
5. 上述都正常后重新插拔一次 USB，再做连接，多数情况下即可恢复。
