# 固件工程与调试环境

> 本文记录机器人固件工程的搭建过程、引脚与参数配置，以及调试中踩过的坑，供后续复现与答辩使用。

## 工程结构与工具链

| 环节 | 选择 | 说明 |
| --- | --- | --- |
| 引脚与时钟配置 | STM32CubeMX 6.18.1 | 图形化配置，生成初始化代码 |
| 工程组织 | CMake + STM32CubeCLT 1.22.0 | CubeMX 的 Toolchain/IDE 选 CMake，便于 CLion 直接打开 |
| 编译器 | arm-none-eabi-gcc 14.3.1 | 随 STM32CubeCLT 安装 |

工程目录为仓库根目录下的 `AIcar/`，其中 `Core/Src/ps2.c`、`Core/Inc/ps2.h` 为自行编写的手柄驱动，其余为 CubeMX 生成的标准结构。

## 手柄驱动设计

- 通信协议与 SPI Mode 3 等效，但**不能用 HAL 的单字节收发**：STM32F1 的 `HAL_SPI_TransmitReceive(…, 1)` 在单字节场景下存在"读 RXNE 前数据未就绪"的已知问题，因此驱动改为直接读写 `SPI_SR` / `SPI_DR` 寄存器，最稳。
- 每次通信时序：片选拉低 → 延时几微秒 → 连续收发 9 字节 → 片选拉高 → 间隔 ≥1ms。间隔太短接收板不会响应。
- 初始化时依次发送"进入配置模式 → 打开模拟模式 → 设置双摇杆模式 → 退出配置"四条命令，使接收板能输出摇杆数据；随后读一次，用第 3 个字节是否为 `0x5A` 判断通信是否正常。

## 调试记录与踩坑

### CLion 中两个 CMake 配置互相污染（10-14）

- **现象**：点击构建后报错 `ninja: error: build.ninja:35: loading 'CMakeFiles/rules.ninja': The system cannot find the file specified.`
- **原因**：CLion 里有两条构建配置——一条是不带后缀的 `Debug`（默认使用系统里的 MinGW 编译器 `D:\Code\ucrt64\bin\cc.exe`），另一条是 `Debug-STM32`（使用 STM32CubeCLT 的 ARM 编译器）。先用前者配置工程时，会在构建目录里写入"使用 MinGW 编译器"的 CMake 缓存；之后换用正确的配置，CMake 检测到编译器变量与缓存不一致，要求清空缓存后重配，配置中断导致 ninja 的规则文件没有生成。
- **解决**：删除被污染的两份构建目录（`cmake-build-debug`、`cmake-build-debug-stm32`），用 ARM 工具链重新配置生成；并**始终只使用 `Debug-STM32` 配置**，避免再次污染。
- **经验**：当同一工程里有多个 CMake 配置、且编译器不同时，每个配置必须使用各自独立的构建目录；一旦缓存被"错误编译器"写过，最省事的做法是直接删掉构建目录重配。
